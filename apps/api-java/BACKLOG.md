Bugs found+fixed during Tier 2 (benefit every module, not just Tier 2):
- **`BaseEntity`/new `CreatedAtEntity`/`IdOnlyEntity` didn't implement `Persistable`** — an entity with an app-assigned id (via `Cuid.generate()` before first save) looks "not new" to Spring Data's default check, so `repository.save()` silently called `em.merge()` instead of `em.persist()`. `merge()` returns a *different* managed copy; code that kept using the original object reference (every module's `create()` — Tier 1 included) got a stale object back with `createdAt`/`updatedAt` (and anything else `@PrePersist` sets) left null. Fixed by implementing `Persistable<String>` with a transient `isNew` flag on all three base classes — root-cause fix, not a per-call-site patch.
- **Literal enum comparisons inside `@Query` JPQL** (e.g. `i.status = com.checkup.pharmacy.common.enums.BatchStatus.ACTIVE`) compiled fine but broke at runtime: Hibernate renders these as an unquoted-cast SQL literal, and Postgres folds unquoted identifiers to lowercase, so the real quoted enum type (`"BatchStatus"`) doesn't match. Fixed by switching every literal enum comparison to the existing `CAST(x AS string) = 'ACTIVE'` text-comparison convention.
- **A null `:search`/`:from`/`:to` parameter bound into `LOWER(CONCAT(...))` or a timestamp `>=`/`<=` comparison** leaves Postgres unable to infer the parameter's type ("could not determine data type of parameter" / "function lower(bytea) does not exist" / "cannot cast type bytea to timestamp") — worse than the already-known null-enum issue (42P18) and not reliably fixable with an in-query `CAST`. Fixed with a new `common/util/DateRange` helper: callers resolve an absent `from`/`to` bound to a wide sentinel range *before* it reaches the query, so the bind value is always a concrete, unambiguous type. `MedicineRepository`, `CustomerRepository`, `DoctorRepository`, and `SupplierRepository`'s `search()` methods (Tier 1) had this same latent bug — **fixed during the Tier 3 session** (`CAST(:search AS string)` applied to every OR'd LIKE branch) and **re-verified live** in a later session (`GET /medicines`, `/customers`, `/doctors`, `/suppliers` all return 200 with no `search` param at all, the actual trigger scenario) — this note had gone stale and kept getting reported as an open bug in status summaries; it isn't one.
- **A just-persisted entity's lazy `@ManyToOne` relation reads back `null`, even when re-queried in the *same* transaction** — Hibernate's persistence-context identity map returns the already-managed (association-still-null) instance instead of re-resolving it from a fresh fetch-joined query. Only a *new* transaction (e.g. a subsequent GET) resolves it correctly. Fixed at each call site by threading through the already-loaded related object (or a batch-fetched id→entity map) instead of relying on `entity.getRelation()` immediately after `save()` — see `PurchasesService.createPO`, `SupplierReturnsService.create`, `StockAuditService.createSession`.

- [x] A4 — Rate limiting — **built and verified live**, two layers, both on `common/ratelimit/RateLimitService` (Redis `INCR`+`EXPIRE` fixed-window counter, fails open on Redis errors):
  1. Tight per-endpoint limits on the auth flows that actually needed brute-force protection: login (5/15min per IP+email, plus a looser 20/15min per-IP-only ceiling to catch email-cycling), register (5/hour per IP), forgot-password (3/hour per IP+email). Runs immediately after `RequestIdFilter` — before Spring Security/JWT/DB work, so a rejected request doesn't burn those resources, but still gets a request id and an access-log line. `/api/v1/health` is exempt (infra probes shouldn't ever trip it for everyone behind the same IP). Verified live with the limit temporarily lowered to 10/min: requests 1-10 pass through to the real (401, unauthenticated) handler, 11+ get a clean 429; health check stays exempt at any volume. **Deliberately generous, not tight** — a single pharmacy's whole staff commonly shares one NAT IP behind one router, so this is sized to catch a scripted attacker, not a busy shift; it layers on top of the per-endpoint limits above, it doesn't replace them.

  Also fixed while building the global layer: **the raw-response-writing error path (`SecurityConfig.writeError`, and the new `GlobalRateLimitFilter`) defaulted to ISO-8859-1**, not UTF-8 — the servlet spec's default writer encoding. Invisible today for `SecurityConfig`'s pure-ASCII "Unauthorized"/"Forbidden" messages, but the rate-limit message's em dash silently mangled into `?` until `response.setCharacterEncoding("UTF-8")` was added to both call sites.

- [ ] **Cold start (~31s) — AppCDS measured and REJECTED, do not retry it.** Spring Boot 3.3's CDS support was tried end to end (`-Djarmode=tools extract` → training run with `-Dspring.context.exit=onRefresh` → `-XX:SharedArchiveFile`). Result over 3 runs each: **31.6/35.2/36.2s without CDS vs 44.6/36.5/35.9s with** — no gain, within noise, and a 113 MB archive to build and ship. The reason is visible in the startup timeline: scanning is only ~3s, Hibernate's EntityManagerFactory ~6s, and **~20s is Spring bean creation and CGLIB/ByteBuddy proxying** — none of which CDS touches. The archive log confirms it, skipping precisely those classes ("Skipping net/bytebuddy/… Old class has been linked", "Skipping com/checkup/…$HibernateProxy$… Unsupported location"). Anything that actually moves this number has to reduce bean count or defer bean creation (`spring.main.lazy-initialization`, which trades startup for first-request latency — a bad trade for a till). Operationally the number rules out scale-to-zero hosting and requires a health-check start period above ~60s.

- [x] A7 — Response compression — **done and measured.** `server.compression` enabled (gzip, JSON/HTML/CSS/JS, 1 KB threshold). - [x] A9 — Structured JSON logging + request IDs — **verified live**: `logstash-logback-encoder` JSON console output; `RequestIdFilter` (highest-precedence, wraps the whole chain including Spring Security) assigns/reuses an `X-Request-Id`, echoes it in the response header, and — critically — emits the one log line a request actually needs to be traceable at all (method/path/status/duration), since without an access-log line a successful request produced *zero* output and the request id had nothing to correlate. `JwtAuthenticationFilter` adds `userId`/`pharmacyId` to the same MDC context once authenticated; all three keys are cleared in `RequestIdFilter`'s `finally` (not scattered across filters) since Tomcat reuses worker threads across requests and a leftover MDC value would leak into the next unrelated request.
- [x] A10 — DB hardening — **all three items were already satisfied; this entry had gone stale, and the one real gap it masked is now closed.** Audited: (1) **PG enum writes via `NAMED_ENUM`** — `@JdbcTypeCode(SqlTypes.NAMED_ENUM)` on every native-enum column across 25 entities; (2) **`Decimal`→`BigDecimal`** — all 18 money-carrying entities use `BigDecimal`, **zero** `float`/`double` money fields anywhere; (3) **`prepareThreshold=0`** — present on the `JDBC_DATABASE_URL`, which correctly targets Supabase's **transaction-mode pooler** (`...pooler.supabase.com:6543` — i.e. we *do* use PgBouncer/Supavisor; self-hosting another pooler in front of it would only add a hop). Hikari's pool is kept deliberately small (`DB_POOL_MAX:5`) because the Free-tier pooler is easily exhausted.

  **The real gap this masked** (now fixed): `prepareThreshold=0` lived *only* in the `.env` URL string — nothing enforced it. A production deploy that set `JDBC_DATABASE_URL` at port 6543 and omitted the parameter would boot cleanly, serve fine on light traffic, and then fail **intermittently under load** (`prepared statement "S_1" already exists`) once concurrency spread transactions across pooled backends — the worst possible thing to discover mid-cutover. Added `config/DatasourceConfigValidator`: fails startup fast if the URL targets the transaction-pooler port (6543) without `prepareThreshold=0`, with a one-line actionable fix in the message. Deliberately narrow (only port `:6543`) so it can never false-positive on a direct 5432 or local Postgres. **Verified live** against a real Postgres bound to host port 6543: missing param → refuses to boot with the actionable error (DB connection itself was fine, proving the *guard* stopped it, not a connection failure); with the param → boots + logs a confirmation; a decoy `:16543` URL → guard correctly does not fire (exact port match, not a loose digit match).
- [x] A11 — Double-submit / duplicate-create protection — **built and verified live**. Money/stock ops (billing invoice + sales return) already had the strongest guard: **client idempotency keys** (a double-submit returns the *same* record, never a duplicate) + `Isolation.SERIALIZABLE` + 409-on-conflict. That leaves the plain creates, which have no natural unique key — a double-click that slips past the frontend's disable-on-submit could create two rows. Added `common/idempotency/DuplicateSubmitGuard` (Redis-backed): fingerprints `(pharmacyId, userId, action, request-body)` and rejects a second identical submission within a 10-second window via `SET key NX EX`, throwing a 409 with a friendly message. **Deliberately not** the full billing-style mechanism (that needs a dedicated DB column + a client-supplied key — a Prisma schema change *and* a frontend change); this is the schema-free, frontend-free equivalent that catches the realistic double-click. **Fails OPEN** (Redis down or unserializable payload → the create proceeds). Wired into 11 create endpoints: customer, supplier, doctor, purchase-order, **GRN** (receipt adds stock — high value), quotation, calendar event, support ticket, and the three supplier money-ops (payment, return, credit-note — none of which had *any* prior double-submit guard). Verified live: identical back-to-back `POST /doctors` → first 201, second 409, exactly **one** row created; a *different* body is not blocked (201); and after the 10s window the same submit succeeds again (it's a short backstop, not a permanent unique constraint). Tradeoff noted in the class javadoc: an identical request that legitimately *failed* is blocked from an identical retry for the window's short duration.

**Bugs found and fixed while building A4/A8/A9** (an edge-case sweep of the session's earlier partial-completion endpoints — calibrate-stock, frequent, reorder-suggestions, stock-audit report, supplier history, uploads — turned up nothing; all handled zero-data/empty-history cases cleanly. These three did surface, all from testing `uploads` specifically, none caught by `mvn compile`):
- **No `spring.servlet.multipart` size config at all** — Spring Boot's *default* (1MB/file) was silently in effect, contradicting `UploadService`'s own intended 10MB check: any file between 1MB and 10MB was being rejected by the framework via an uncaught `MaxUploadSizeExceededException` before `UploadService` ever ran, well below the limit the code claimed to enforce. Fixed by setting `max-file-size: 10MB` / `max-request-size: 11MB` explicitly, and adding a `GlobalExceptionHandler` handler for `MaxUploadSizeExceededException` (→ clean 400) and its supertype `MultipartException` (→ clean 400, covers "no file part sent at all") — both previously fell through to the generic 500.
- **A barcode containing a literal `/` produced a raw Tomcat HTML 400 page**, not our JSON error envelope, because the servlet container rejects an encoded slash in a path segment before the request ever reaches Spring. Investigated fixing it via a `TomcatConnectorCustomizer` (`encodedSolidusHandling=decode`) — confirmed *that half* worked (the container-level HTML page went away), but it then surfaced a second-order conflict with Spring Security's `StrictHttpFirewall`, which rejects encoded slashes *by design* specifically to prevent path-based authorization-rule bypass, and the combination produced a confusing 401 instead. Reverted rather than weakening a deliberate security control: barcodes never legitimately contain `/` (EAN/UPC/Code128 are numeric/alphanumeric only), so this stays a non-JSON 400 for what both other tiers of the framework — Tomcat and Spring Security's firewall — agree is malformed input.
- **`MissingServletRequestParameterException` was never actually the exception thrown for "no file uploaded"** — it's `MultipartException` (see above); an earlier version of this fix targeted the wrong exception type based on the finding methodology's initial hypothesis (a plausible guess, since it's the usual exception for a missing `@RequestParam`) rather than the actual stack trace, and was corrected against the real one.
- A stale BACKLOG.md note claiming the null-search-parameter bug (see Tier 2 notes above) was "likely" still unfixed in `MedicineRepository`/`CustomerRepository`/`DoctorRepository`/`SupplierRepository` had itself gone stale — it *was* fixed, during the Tier 3 session, and had simply never been updated here afterward. Re-verified live (all four `search()` endpoints handle a fully-omitted `search` param correctly) and the note corrected — this had been repeated as an open issue in at least one status summary since.

### Notes
- **Schema stays owned by Prisma** (`packages/database`); JPA is read/write only (`ddl-auto: none`).
- Every module follows `modules/package-info.java`: thin controllers, tenant-scoped
  queries, entities never returned directly (map to `dto/`), all responses wrapped
  in `ApiResponse`.
- Critical path to a usable app: **Tiers 1–3**. Tiers 4–5 + some integrations follow.
- **Query-parameter gotchas to keep following** (all found the hard way in Tier 2 — see the bug list above for detail):
  - Enum columns: compare as `CAST(x.field AS string) = 'VALUE'` (a plain string literal or bind param) — never `x.field = com.checkup...SomeEnum.VALUE` embedded in JPQL, and never bind a raw enum-typed parameter that might be null.
  - Optional date-range filters: resolve `from`/`to` via `common/util/DateRange.from()/.to()` in the *service*, and write the repository query's comparison unconditionally (no `:from IS NULL OR`) — a genuinely null `Instant` bound into a timestamp comparison breaks Postgres's parameter-type inference and no in-query `CAST` reliably fixes it.
  - Optional text-search filters (`LOWER(CONCAT('%', :search, '%'))`): still cast the parameter — `LOWER(CONCAT('%', CAST(:search AS string), '%'))` — when `:search` can be null.
  - After `repository.save(newlyConstructedEntity)`, don't reach for `entity.getSomeLazyRelation()` for the response — it's null (see the Persistable/lazy-relation bugs above). Either use the object you already loaded (pass it through explicitly), or batch-fetch a lookup map, matching `InventoryService.enrich()`.
